## Finding P0-001 — event-only CodeManager still scans all Windows processes every 10 seconds

### Runtime evidence

A 12-minute Windows CPU sample after retiring the old LOLDataSystem duplicate Startup chain showed a new short-lived `powershell.exe` approximately every 10 seconds. The processes were children of the FAR2Farm `node.exe` process and executed:

```powershell
Get-CimInstance Win32_Process |
  Select-Object Name,ProcessId,ParentProcessId,SessionId,ExecutablePath,CommandLine,CreationDate |
  ConvertTo-Json -Compress -Depth 3
```

These short-lived PowerShell processes produced the visible CPU spikes even while the QQ Farm account was healthy.

### Root cause

Production is intentionally configured for event-only Code refresh:

```text
FARM_CODE_AUTO_REFRESH=1
FARM_CODE_SCHEDULED_REFRESH=0
```

Expected policy:

```text
healthy account -> no proactive Code refresh
WS400 / valid kickout / manual trigger -> refresh Code
failed recovery -> retry
```

However `CodeManager` still created a 10-second timer. Every idle `tick()` called `desktopSessionRegistry.getStatus()`. `getStatus()` refreshes bindings by starting PowerShell and enumerating the whole Windows process table. `CodeManager.getStatus()` also called the same expensive path, so health/WebUI reads could cause additional scans.

The installed `FARM_CODE_SCHEDULED_REFRESH=0` flag was not used by `code-manager.js` to suppress idle session scans.

### Fix in this branch

- Honor `FARM_CODE_SCHEDULED_REFRESH` explicitly.
- In event-only mode, healthy accounts have no scheduled `nextRefreshAt`.
- Keep the cheap JavaScript timer only as a retry scheduler; idle ticks return before touching the desktop-session registry.
- Take a fresh desktop-session snapshot only when startup or actual due recovery work requires it.
- Reuse the due-work snapshot inside `refreshAccount` to avoid a second process enumeration in the same recovery cycle.
- Make `CodeManager.getStatus()` / `getAccountStatus()` read the cached snapshot instead of rescanning Windows.
- Preserve WS400 / valid kickout / manual event-driven refresh and failed-recovery retry behavior.
- When a retry finds the desktop Session missing/mismatched, reschedule using `retryMs` instead of rescanning on every poll tick.

### Regression test

Added:

```text
core/scripts/qq-code-manager-event-only-selftest.js
```

The self-test asserts:

- startup takes one desktop snapshot;
- repeated status reads cause no additional desktop scans;
- repeated idle event-only ticks cause no additional desktop scans;
- healthy idle state performs no Provider refresh;
- a WS400-style trigger still performs one fresh session scan and one Provider refresh;
- after successful event-driven recovery, no periodic refresh deadline is reintroduced.

Local isolated execution of the regression test passed, and the modified `code-manager.js` passed `node --check` before the branch update.
