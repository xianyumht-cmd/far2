## Finding P0-001 — event-only CodeManager still scans all Windows processes every 10 seconds

### Runtime evidence

A 12-minute Windows CPU sample after retiring the old LOLDataSystem duplicate Startup chain showed a new short-lived `powershell.exe` approximately every 10 seconds. The processes were children of the FAR2Farm `node.exe` process and executed:

```powershell
Get-CimInstance Win32_Process |
  Select-Object Name,ProcessId,ParentProcessId,SessionId,ExecutablePath,CommandLine,CreationDate |
  ConvertTo-Json -Compress -Depth 3
```

These short-lived PowerShell processes produced the visible CPU spikes even while the QQ Farm account was healthy.

### Root cause

Production is intentionally configured for event-only Code refresh:

```text
FARM_CODE_AUTO_REFRESH=1
FARM_CODE_SCHEDULED_REFRESH=0
```

Expected policy:

```text
healthy account -> no proactive Code refresh
WS400 / valid kickout / manual trigger -> refresh Code
failed recovery -> retry
```

However `CodeManager` still created a 10-second timer. Every idle `tick()` called `desktopSessionRegistry.getStatus()`. `getStatus()` refreshes bindings by starting PowerShell and enumerating the whole Windows process table. `CodeManager.getStatus()` also called the same expensive path, so health/WebUI reads could cause additional scans.

The installed `FARM_CODE_SCHEDULED_REFRESH=0` flag was not used by `code-manager.js` to suppress idle session scans.

### Fix in PR #58

- Honor `FARM_CODE_SCHEDULED_REFRESH` explicitly.
- In event-only mode, healthy accounts have no scheduled `nextRefreshAt`.
- Keep the cheap JavaScript timer only as a retry scheduler; idle ticks return before touching the desktop-session registry.
- Take a fresh desktop-session snapshot only when startup or actual due recovery work requires it.
- Reuse the due-work snapshot inside `refreshAccount` to avoid a second process enumeration in the same recovery cycle.
- Make `CodeManager.getStatus()` / `getAccountStatus()` read the cached snapshot instead of rescanning Windows.
- Preserve WS400 / valid kickout / manual event-driven refresh and failed-recovery retry behavior.
- When a retry finds the desktop Session missing/mismatched, reschedule using `retryMs` instead of rescanning on every poll tick.
- Wire the event-only regression into the normal `qr:code-manager-selftest` command.

Regression coverage asserts startup scan count, idle scan count, status-read scan count, Provider call count and WS400 event recovery behavior.

Status: **FIX CANDIDATE OPEN — PR #58, production unchanged.**

## Finding P0-002 — Code capture clipboard fallback can create excessive event-time PowerShell

Source audit of runtime shell creation found no second autonomous healthy-idle process-scan loop after P0-001. It did find that `windows-runtime-code.js` used `Get-Clipboard -Raw` on every 250 ms Code-capture wait iteration when `_code.txt` had not appeared yet.

Because every clipboard read starts `powershell.exe`, one real recovery event could create approximately four PowerShell processes per second until capture completed or timed out.

PR #59 keeps `_code.txt` as the 250 ms fast path but moves clipboard to a compatibility fallback: first read after 1 second, then at most once every 2 seconds. An isolated regression run passed for the throttle logic.

Status: **FIX CANDIDATE OPEN — PR #59, production unchanged.**

Detailed audit: `docs/P0_002_RUNTIME_SHELL_AUDIT_2026-08-20.md` in PR #59.

## Finding P0-003 — fertilizer async interval can overlap write-capable checks

Timer audit found that the main Farm and Friend loops are sequential, Worker status sync is in-memory, heartbeat is intentional connection keepalive, and startup friend import is time-bounded. One write-capable timer remained unsafe: fertilizer auto-purchase uses a plain `setInterval()` around an async purchase/check callback.

The configured interval can be as low as one minute. If a network/RPC call exceeds the interval, another timer invocation could enter the same purchase path concurrently.

PR #60 adds an in-flight guard with `finally` cleanup. An isolated stubbed overlap regression passed: the second concurrent invocation was skipped and a later invocation ran after guard cleanup.

Status: **FIX CANDIDATE OPEN — PR #60, production unchanged.**

Detailed audit: `docs/P0_003_TIMER_AUDIT_2026-08-20.md` in PR #60.

## P1 recovery audit

The current QQ recovery ordering remains safety-oriented:

```text
trigger
  -> account/global/config guards
  -> Session identity check
  -> Provider availability
  -> obtain fresh Code
  -> stop old Worker
  -> bounded wait/force-kill path
  -> persist fresh Code
  -> start replacement Worker
```

Per-account `inFlight` prevents concurrent refresh tasks; `startWorker()` refuses a duplicate account Worker; Provider/session failures occur before the old Worker is stopped; failed recovery uses bounded retry rather than a tight loop.

Status: **SOURCE AUDIT PASS — no new concurrent-Worker/tight-retry defect confirmed in this pass.**

## P2 read/status side-effect audit

Observed WebUI polling:

- CodeManager status: every 5 seconds;
- Health Center: every 10 seconds.

Before P0-001 those reads could indirectly call the live Desktop Session registry and spawn PowerShell. PR #58 converts CodeManager status reads to cached Session state, so normal WebUI health/status polling no longer needs a live Windows process scan.

The isolated Code Agent `/v1/health` remains an explicit live readiness/identity probe and may inspect the Windows QQ process tree; it is used on actual recovery/provider readiness paths, not by normal Health Center polling.

`desktop-session-registry.getStatus()` is explicitly classified as a live refresh operation, not a cheap/pure getter: it scans, updates binding state and persists the registry. Higher-level repeated status reads must use cache rather than call it.

Status: **SOURCE AUDIT PASS AFTER PR #58 for normal WebUI polling.**

## P4 persistence audit

Positive finding: `json-db.js` already used temporary-file + rename semantics for callers of `writeJsonFileAtomic()`.

### Finding P4-001 — accounts JSON corruption could become silent empty state

Old `readJsonFile()` returned the same fallback for missing/read/parse failures. `store.loadAccounts()` uses an empty-account fallback, so an existing malformed `accounts.json` could be treated as empty and later overwritten by a normal mutation. Syntactically valid but structurally invalid state such as `{}` had the same risk.

PR #61 introduces critical JSON fail-closed behavior for `accounts.json`:

- missing file retains first-run fallback;
- existing empty/malformed/unreadable/invalid-shape file raises `critical_json_corrupt`;
- readable rejected bytes are preserved to a deterministic `.corrupt-<mtime>-<size>.bak`;
- non-critical cache/artifact JSON remains tolerant.

The current shape-hardening regression was executed in the audit sandbox with `node --check` + selftest and passed.

Status: **FIX CANDIDATE OPEN — PR #61, production unchanged.**

### Finding P4-002 — user/security/card state used direct overwrite and tolerant reset

Full `user-store.js` audit expanded the initial finding. Direct `fs.writeFileSync` overwrite was used for:

- `users.json`;
- `cards.json`;
- `login-attempts.json`;
- `login-logs.json`;
- `card-claim.json`.

Several corresponding loaders reset to empty/default state after parse failure. That can erase user/card data, active login lockout/rate-limit state, or card-claim history after a partial/corrupt write. Critical save helpers also swallowed write failures, allowing callers to believe a mutation succeeded when persistence failed.

Stacked PR #62 (base PR #61 branch) changes all five writers to atomic JSON persistence and extends critical fail-closed reads/shape validation to `users.json`, `cards.json`, `login-attempts.json` and `card-claim.json`. Critical write failures propagate. `login-logs.json` intentionally remains tolerant on read so an audit-log problem cannot block authentication, but its successful writes are atomic.

The #62 branch was synchronized with the latest #61 shape-hardening using a normal merge commit: relative to #61 it is `ahead`, `behind=0`, and the PR is mergeable.

Status: **FIX CANDIDATE OPEN — PR #62, stacked on #61, production unchanged.**

### Finding P4-003 — registration/renewal was not atomic across users.json + cards.json

P4-002 makes each file individually atomic, but `registerUser()` and `renewUser()` are one business operation that mutates both user entitlements and card inventory. The old `saveUsers() -> saveCards()` sequence can still split if the process crashes or the second file fails after the first file commits.

Stacked PR #63 (base PR #62 branch) adds a crash-recoverable transaction journal:

```text
prepare before/next journal
-> atomic users.json
-> atomic cards.json
-> remove journal
```

On a leftover journal, recovery recognizes both-next as committed, both-before as not committed, rolls expected mixed before/next states back to before, and fails closed on unknown divergence. `registerUser()` / `renewUser()` also restore in-memory before-state when a persistence error is thrown.

The transaction service `node --check` + crash-recovery selftest passed in the audit sandbox, including injected second-file failure and unknown-divergence fail-closed cases.

Status: **FIX CANDIDATE OPEN — PR #63, stacked on #62, production unchanged.**

Detailed P1/P2/P4 analysis: `docs/P1_P2_P4_AUDIT_2026-08-20.md`. P4-003 detail is in `docs/P4_003_USER_CARD_TRANSACTION_2026-08-20.md` on PR #63.

## P5 test/documentation drift audit

The intended event-only Code policy is consistent in current README/milestone/install documentation. P0-001 was implementation drift: documentation and production environment were event-only while old CodeManager still scanned Windows every 10 seconds. PR #58 closes that mismatch.

Two engineering-process gaps remain:

1. `main` currently has no `.github/workflows` CI gate, so self-tests are not automatically required on PR/push.
2. `core/package.json` still has the default `test` script as an intentional failing placeholder even though many real self-test commands exist.

These are tracked as post-merge test-infrastructure work. The eventual default test/CI aggregate must include only offline/safe tests and must not accidentally run live QQ/Windows/Farm write probes.

Status: **SOURCE AUDIT PASS WITH FOLLOW-UP PROCESS GAP RECORDED.**

Detailed audit: `docs/P5_TEST_DOC_DRIFT_AUDIT_2026-08-20.md`.
