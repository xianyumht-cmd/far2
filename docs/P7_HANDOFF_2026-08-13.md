### 4.2 重要：PR #39 原始实现存在一个外层调度遗漏

在 P7D 开始前复核主链时发现：

`friend.js` 内部已经支持“经验满后只继续护主犬”，**但 Worker 外层 `runHelpTick()` 仍保留旧逻辑：经验满后直接 return。**

原状态相当于：

```text
Worker runHelpTick
  -> 经验满
  -> return
  -> friend.js 根本进不去
```

这会让 P7C 内部策略在生产调度中失效。

因此不要把 PR #39 单独当成最终 P7C。

### 4.3 最终补丁

PR #40：`fix: complete P7C scheduler gate`

最终功能 commit：

```text
8c957cc345cec545e5b422d1f3fb502f0c7e8e11
fix: let guard dog help pass exp-limit scheduler gate
```

当前正确链：

```text
runHelpTick()
  -> 若未达到经验上限：正常进入 checkFriends({ onlyHelp: true })
  -> 若达到经验上限：
       -> 查当前账号缓存中的有效护主犬数量
       -> 0 个：继续保持旧行为，跳过本次帮助 tick
       -> >=1 个：进入 checkFriends({ onlyHelp: true })
            -> friend.js 内部排序/过滤
            -> 只允许有效护主犬好友继续帮助
            -> 普通好友不帮
```

这同时满足：

- 不为了找护主犬去额外扫 97 个好友；
- 已知没有护主犬时不增加请求；
- 已知有护主犬时才让内部精确策略工作。

## 7. 不要重复的路线

### 7.1 不要新增“扫所有好友狗”的启动任务

当前约 97 个有效好友。为了找护主犬而额外逐个 `Enter` 会制造明显请求压力，也违背本轮已确定的 opportunistic 设计。

正确路线：从正常帮助 / 偷菜 / 手动详情已经发生的 `Visit.Enter` 中学习 dog state，然后缓存。

### 7.2 不要猜 `DogService.GetDogInfo(host_gid)` 能查询好友狗

当前真实验证的 `DogService.GetDogInfo` 是自己账号 empty-body 路径。好友狗来自 `Visit.Enter` field 3。

没有新的真实抓包前，不要把 `host_gid` 塞进 GetDogInfo，也不要把自己狗协议和好友 brief dog 协议强行合并。

### 7.3 不要暴露好友 dog field 3 的原始 payload

P7B 从一开始就故意不暴露 raw/base64 bytes，只保留安全字段摘要。不要为了“方便调试”把原始字段直接返回 WebUI。

### 7.4 不要把 `remainingSeconds` 擅自重新命名成更强语义

当前证据支持“随时间按秒下降的剩余有效时长”。

没有证据前不要改成：

```text
保护时间
狗到期时间
护主技能到期时间
```

### 7.5 不要只改 `friend.js` 就宣称 P7C 完成

PR #40 已证明 Worker 外层 scheduler gate 也必须配合。未来改帮助经验上限逻辑时，必须同时检查：

```text
worker.js runHelpTick
friend.js help filter/order
friend-dog-state.js cache/policy
```

### 7.6 不要开通用任意 BuyGoods API

P7D 故意做宠物商店专用安全入口。不要改成“前端给 shopId/goodsId/price 就直接 BuyGoods”。

服务器必须重读：

```text
shop type
商品存在性
unlocked
boughtNum
limitCount
price
```

### 7.7 不要信任客户端 price
