# FAR2 P0-003 Timer Audit — 2026-08-20

## Goal

Classify long-lived production timers and verify that healthy-idle work is intentional, bounded, stoppable, and protected against overlap where the callback can perform network/write work.

## Reviewed timers

### CodeManager

- 10-second timer exists for retry/scheduled dispatch.
- P0-001 / PR #58 changes event-only idle ticks to return before live Windows Session scanning.
- retry work is bounded by `retryMs` and `inFlight` per account.

Disposition: acceptable after P0-001.

### Worker heartbeat

- 25-second heartbeat is an expected Farm connection keepalive.
- tied to Worker lifecycle and cleared on stop/close.

Disposition: expected business timer.

### Worker status sync

- 3-second status sync computes status from in-memory Worker state.
- it only sends when the serialized status changes or the 8-second send horizon expires.
- no Windows process scan or external shell is involved.

Disposition: acceptable low-cost runtime telemetry.

### Farm check loop

- uses sequential `setTimeoutTask`: next run is scheduled only after the current `checkFarm()` completes.
- prevents normal periodic overlap by construction.

Disposition: acceptable.

### Friend check loop

- uses sequential timeout scheduling after `checkFriends()` returns.
- does not stack another recurring run while the current pass is executing.

Disposition: acceptable.

### Startup runtime friend import

- 2-second artifact poll, Windows-only.
- bounded to startup; stops once configured accounts import successfully or after its 10-minute timeout.
- reads local capture artifacts rather than spawning PowerShell.

Disposition: bounded startup poll.

### Admin session cleanup

- 5-minute cleanup timer.
- bounded in-memory/session maintenance and cleared on server close.

Disposition: acceptable.

### Code Agent post-capture identity loop

- short 150ms live identity polling only during a real Code capture.
- bounded by the Agent identity timeout (default 8 seconds).
- not a healthy-idle timer.

Disposition: event-bound; retain for identity safety.

## Finding P0-003-A — fertilizer purchase timer could overlap

`farm-scheduler.js` used a plain `setInterval()` for fertilizer purchase checks. The configured interval is normally long, but it is allowed down to one minute. The async callback had no in-flight guard. A slow or hung purchase/check RPC could therefore let the next interval invocation enter the same purchase logic concurrently.

This is a correctness risk because the callback can perform purchase write operations.

### Fix in this branch

- add a per-service `fertilizerBuyCheckRunning` guard;
- an overlapping invocation returns without entering purchase logic;
- guard always clears in `finally` on success or failure;
- a later interval can run normally after the previous check finishes;
- expose read-only `isFertilizerBuyCheckRunning()` for contract testing.

### Regression

The existing `farm-scheduler-selftest.js` now holds the first fake purchase open, invokes a second check, and verifies:

- the second overlapping call is skipped;
- purchase logic is entered only once;
- after the first call resolves, the guard clears;
- a subsequent check can run normally.

## Result

No second high-cost healthy-idle timer equivalent to P0-001 was found in the reviewed core runtime. One write-capable overlap defect was confirmed and fixed in this branch.

Production deployment remains a separate gate.
