# FAR2 Feature Gap Audit — 2026-08-13

状态：**CURRENT ROADMAP INPUT**

## 1. 审计目标

本审计用于回答一个长期问题：FAR2 当前基于的公开版本，与作者 2026-04 之后继续维护但未公开完整源码的版本相比，还差哪些功能，哪些功能 FAR2 已经独立补回或超过，以及下一步应该先做什么。

对照来源：

- 公开源码基线：`XyhTender/qq-farm-automation-bot`，公开功能代码基本截止 2026-03-31；
- 后续更新日志：`https://gitee.com/xlzcandy/qq-classic-farm-update-log`；
- 后续日志当前覆盖到 2026-06-26 V2.4.7；
- FAR2 对照基线：2026-08-13 `main`，运行健康中心合并后版本。

> 重要：后续日志只能证明“作者后续版本声明做过什么”，不能证明实现细节，也不能直接复制不存在的私有源码。本项目只把它当作功能需求清单，具体实现以当前游戏协议、FAR2 现有代码和真实测试为准。

## 2. 状态定义

| 标记 | 含义 |
|---|---|
| ✅ | FAR2 当前已经具备，或核心能力已达到该项目标 |
| 🟡 | FAR2 有底层协议/代码基础，但缺正式 API、UI、完整流程或功能不完整 |
| ❌ | 当前没有发现对应正式实现 |
| 🔁 | 后续版的需求已被 FAR2 当前方案替代，而且当前方案更符合现有生产架构 |

## 3. 关键源码事实

### 3.1 图鉴不是从零开始

`core/src/proto/illustratedpb.proto` 已存在：

- `GetIllustratedListV2`
- 图鉴条目：seedId、解锁、已种植、种植数、收获数、分类、奖励状态
- `ClaimAllRewardsV2`

但当前没有对应正式 service、worker API、WebUI 页面。

结论：**图鉴 = 🟡，协议地基已在仓库。**

### 3.2 种子商店 / 宠物商店也不是从零开始

`core/src/proto/shoppb.proto` 已明确包含：

- 商店类型 1：道具
- 商店类型 2：种子
- 商店类型 3：宠物
- `ShopProfiles`
- `ShopInfo`
- `BuyGoods`

同时 `core/src/services/farm.js` 已经有 `getShopInfo()` / `buyGoods()`，当前自动种植也会查询种子商店并购买种子。

但当前 WebUI 没有独立的种子商店 / 宠物商店页面，也没有把这套能力整理成正式用户接口。

结论：**种子商店 = 🟡；宠物商店 = 🟡（仅商店层，宠物系统本体仍缺失）。**

### 3.3 单土地操作底层基本已经存在

`core/src/services/farm.js` 已有按 landId 操作的：

- `removePlant(landIds)`
- `fertilize(landIds, fertilizerId)`
- `upgradeLand(landId)`
- 浇水 / 除草 / 除虫 / 收获等接口也接受 landIds

当前 `FarmPanel.vue` / `LandCard.vue` 主要还是展示 + 批量操作，没有给每张土地卡片做正式的单地块操作入口。

结论：**单土地操作 = 🟡，后端底层成熟，主要缺 API/UI 收口。**

### 3.4 2x2 已经被 FAR2 独立补回

当前 `farm.js` 会识别 master/slave land、`plantSize`、占用地块，并避免把 2x2 的副地块当空地重复种植；`LandCard.vue` 也会显示合种尺寸和季节信息。

结论：**2x2 基础能力 = ✅。**

### 3.5 QQ 好友与 Code 刷新不能再按后续旧日志判断

FAR2 已真实验收：

- 103 GID / 275 openId 上游好友关系数据；
- 97 位当前有效农场好友；
- 帮助 / 巡查 / 偷菜实际运行；
- WS400 / kickout 后 exact-UIN Provider 自动刷新 Code；
- 新 Worker 自动恢复登录；
- 不依赖固定小时刷新 Code。

因此后续日志中“QQ 好友接口修复”“QQ 定时刷新 Code 一直偷菜”等项目不再是 FAR2 缺口。

结论：**QQ 完整好友链 / Code 自动恢复 = 🔁。**

## 5. 当前缺口按领域归并

### A. 商店 / 图鉴（最适合先做）

- 🟡 图鉴读取
- 🟡 图鉴奖励领取
- 🟡 种子商店
- 🟡 图鉴未解锁种子联动购买
- 🟡 道具商店扩展
- 🟡 宠物商店商品层
- ❌ 活动限时商店
- ❌ 钻石商店
- ❌ 神秘商店

优势：基础 proto 和部分 Shop 调用已经存在，投入产出最高。

### B. 个人土地交互（第二优先）

- 🟡 单地块铲除
- 🟡 单地块普通/有机施肥
- 🟡 单地块升级
- 🟡 一键铲除全部
- ❌ 紫土地类型/施肥范围
- ❌ 变异标识/详情
- 🟡 施肥延迟可配置
- ❌ 收获延迟可配置

优势：大多数底层 RPC 已经存在，主要是 API/UI 产品化。

### C. 宠物 / 狗狗（较大新模块）

- 🟡 宠物商店商品协议已有
- ❌ 狗狗状态
- ❌ 护主犬好友识别
- ❌ 狗狗购买后的管理/穿戴/喂养
- ❌ 狗窝/装扮联动
- ❌ 狗狗资本模式

需要先补当前协议事实，不能只靠旧日志猜字段。

### D. 图鉴之外的展示系统

- ❌ 个人生涯
- ❌ 头像框/装扮购买与穿戴
- ❌ 变异详情

这些价值可见，但协议地基比图鉴/Shop 少。

### E. 活动系统

- ❌ 自动购买活动种子
- ❌ 节气礼包
- ❌ 助威活动
- ❌ 黄金虫
- ❌ 南瓜/其他限时商店
- ❌ 钻石活动礼包

### F. 微信好友管理

- ❌ 申请列表 UI

- ❌ 按等级批量删除

## 6. 不再追的旧功能

默认不进入 FAR2 Roadmap：

- 秒偷；
- 蹲守；
- 自动刷变异；
- 为“防封”而加入代理/节点复杂度；
- 健康账号按固定时间反复刷新 Code；
- 已被 FAR2 V4 好友链替代的手工 GID 补丁式方案。

这些要么后续日志自己已经删除，要么已经有更稳定的 FAR2 方案。

## 7. 当前开发优先级

### P0 — 先收掉一个真实稳定性问题

**限制 Windows 生产环境自动启动 Worker 的范围。**

健康中心实机已经证明：当前保存两个账号时，`startAllAccounts()` 会把两个 Worker 都拉起；而当前生产规则是一台 Windows 只运行当前 Provider target 对应的一个 QQ。

目标：

- 如果存在 `FARM_CODE_PROVIDER_TARGETS(_B64)`，启动时只自动启动匹配 Provider target UIN 的保存账号；
- 例如当前机器只启动 `232`，`4476` 保持 idle；
- 不影响手动点击启动其他账号；
- 没有 Provider targets 的通用部署仍保留原有自动启动语义；
- 不修改 Code 获取、好友 V4、偷菜逻辑。

### P1 — 图鉴 + 种子商店

第一批正式追赶功能。

建议拆为：

1. 图鉴只读列表；
2. 显示种子名/图片、是否解锁、种植/收获进度、可领奖状态；
3. 图鉴奖励领取；
4. 种子商店列表；
5. 单个购买；
6. “图鉴缺失且可购买”筛选；
7. 一键每种购买 1 份（必须二次确认、展示预计总成本）。

为什么第一：

- 已有 `illustratedpb.proto`；
- 已有 `shoppb.proto`；
- 已有 `ShopInfo/BuyGoods`；
- 已有 Plant/Item 配置与图片；
- 对自动挂机主链侵入很低；
- 能直接补上 04-18、04-23 两轮核心缺口。

### P2 — 单土地控制 + 紫土地

- LandCard 单块铲除；
- 单块普通/有机施肥；
- 单块升级；
- 全部铲除二次确认；
- 紫土地识别/颜色/施肥范围；
- 补可配置施肥/收获延迟。

### P3 — 变异展示

先只读：

- 自己土地 mutation 标识；
- 好友土地 mutation 详情；
- 不恢复“刷变异”。

### P4 — 宠物 / 狗狗

先做协议发现和只读状态，再做购买/喂养/护主犬策略。不要从“宠物商店能买狗”直接跳到猜完整狗系统。

### P5 — 个人生涯 / 装扮 / 活动框架

最后统一补：

- 个人生涯；
- 头像框/装扮；
- 通用活动商店；
- 节气礼包、助威、黄金虫、钻石/神秘商店等版本性内容。

## 8. 后续执行原则

1. 以后不再问“内部版还有什么”，优先查本文。
2. 后续日志是产品需求参考，不是源码真相。
3. 已有 proto/底层 RPC 的功能优先产品化，避免无意义重新抓包。
4. 对当前 proto 不足的模块，先只读探测，再写操作接口。
5. 活动、宠物等强版本相关模块必须真实运行验证，不能按 4～6 月旧字段硬编码。
6. 不因为追更新日志破坏已经验收的 CodeManager、V4 好友、单机一目标 QQ 生产边界。
7. 新功能默认先做到只读/安全，再逐步开放购买、领取、修改等写操作。
