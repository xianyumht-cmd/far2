# FAR2 P1 / P2 / P4 Production Audit — 2026-08-20

## P1 — CodeManager / Session / Worker recovery

### Recovery ordering

Current QQ recovery order is safety-oriented:

```text
WS400 / valid kickout / manual
  -> per-account triggerRefresh
  -> verify configured account + global enable
  -> acquire/verify Windows Session identity
  -> verify targeted Provider availability
  -> obtain fresh Code
  -> only then stop the old Worker
  -> wait for Worker exit (bounded)
  -> persist fresh Code
  -> start replacement Worker
```

The old Worker is not stopped before the Provider has returned a fresh Code. Provider/session failures therefore leave the existing Worker record intact instead of destroying the last runnable state.

### Concurrency / retry

- `inFlight` is keyed per account, so one account cannot run two concurrent Code refresh tasks.
- Worker `startWorker()` refuses to create a second Worker when the account already has one.
- Worker stop has a bounded force-kill fallback; CodeManager waits for the Worker to disappear before starting the replacement.
- failed Provider/session recovery schedules `retryMs` rather than a tight immediate loop.
- P0-001 additionally prevents event-only idle timer ticks from performing live Session scans when no retry is due.

Disposition: no new P0/P1 concurrent-Worker or tight-retry defect confirmed in this pass. Keep the existing identity fail-closed and replacement ordering unchanged.

## P2 — read/status side effects

### WebUI polling

- `CodeManager.vue` polls `/api/code-manager/status` every 5 seconds.
- `HealthCenter.vue` polls `/api/runtime-health` every 10 seconds.
- runtime health builds its view from account/Worker state, account logs, persisted friend status and CodeManager status; it does not intentionally invoke a Worker Farm RPC.

Before P0-001, `CodeManager.getStatus()` performed a live Desktop Session refresh, so both UI polling paths could indirectly launch PowerShell/CIM scans.

PR #58 changes CodeManager status reads to cached Desktop Session state. After that change, normal CodeManager/HealthCenter polling is not a live Windows process probe.

### Isolated Code Agent health

`/v1/health` on the isolated Code Agent intentionally performs a live QQ/Session identity inspection. That path can use the desktop Session process snapshot. It is not called by the normal HealthCenter polling path; the targeted Provider invokes it while preparing a real Code recovery.

Disposition: keep this as an explicit live readiness probe for recovery safety. Do not route normal 5s/10s WebUI polling to it.

### Desktop Session registry naming/side effect

`desktop-session-registry.getStatus()` is not a pure getter: it calls `refreshBindings()`, performs a process scan, updates timestamps/status and persists the registry. After PR #58 this is no longer on normal CodeManager status polling, but callers must continue to treat it as a live refresh operation.

Disposition: no hot-path rewrite required after P0-001, but future callers must not use it as a cheap status getter. Cached status should be exposed at higher layers where repeated reads are needed.

## P4 — persistence / restart

### Atomic writer

`json-db.js` writes JSON through a process/timestamp temporary file followed by rename and temporary-file cleanup. Core stores that use `writeJsonFileAtomic()` therefore have crash-resistant replacement semantics compared with direct overwrite.

### Finding P4-001 — critical JSON parse failure silently falls back

`readJsonFile()` currently catches file read/JSON parse errors and returns the caller fallback without distinguishing:

- file does not exist;
- empty file;
- permission/read failure;
- malformed/corrupt JSON.

`store.loadAccounts()` uses that helper with an empty-account fallback. A later account mutation can therefore save the fallback state and overwrite a malformed `accounts.json`, turning one corruption event into silent account-data loss.

This requires a separate fail-closed design rather than a quick global behavior change because many non-critical cache/artifact callers intentionally rely on tolerant reads.

Required fix design:

1. add an explicit strict/diagnostic JSON read path for critical state;
2. distinguish missing from corrupt;
3. refuse mutations of critical state when the source file is corrupt/unreadable;
4. preserve/backup the corrupt bytes for recovery;
5. add fixture tests for missing/valid/corrupt/partial JSON and mutation refusal.

Status: **OPEN — separate P4 fix required.**

### Finding P4-002 — login security state still uses direct overwrite

`user-store.js` writes `login-logs.json` and `login-attempts.json` with direct `fs.writeFileSync()` instead of the atomic JSON writer. A process crash during overwrite can leave partial JSON; the corresponding load functions catch parse errors and reset the in-memory structure.

For `login-attempts.json`, silent reset can discard current rate-limit/lockout state after corruption.

Required fix:

- migrate these two writers to `writeJsonFileAtomic()`;
- preserve current max-log trimming and in-memory behavior;
- add a no-real-files fixture/selftest around atomic save/load behavior where practical.

Status: **OPEN — separate P4 fix required.**
